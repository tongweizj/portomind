# 后续路线图

以下能力不属于当前单用户交付基线，应逐项设计和验收，不建议同时开发。

## P1：登录和多用户

先建立 User、Portfolio 所有权和资源级授权，再开放公网访问。需要密码哈希或外部身份提供商、会话/Token 撤销、速率限制、审计日志和数据迁移。所有现有查询必须强制加入 `ownerId`，这是其他协作功能的前置条件。

## P2：CSV 导入

采用“上传 → 字段映射预览 → 校验 → 幂等导入 → 错误报告”流程。必须定义券商模板、日期/数字区域格式、重复交易键和整批回滚策略，不能直接把 CSV 行写入交易集合。

## P3：汇率换算

先定义组合基准币种、汇率来源、时间点和缺失汇率策略。历史持仓必须使用历史汇率，不能用今天汇率重算过去市值；原币种金额与换算金额应同时保留。

## P4：移动端

优先完成响应式 Web：组合概览、交易录入、日志表格和图表触摸交互。指标是 360px 宽度无横向溢出、核心操作可用、表单键盘类型正确，再决定是否需要原生应用。

## P5：Docker

在运行模型稳定后提供前端、API、MongoDB 的 Compose 配置，加入健康检查、非 root 用户、只读镜像、持久卷、备份恢复和单一调度器所有权。密钥只通过运行时 secret/env 注入。

## P6：自动再平衡通知

保持“只生成建议、不自动交易”的安全边界。先实现站内通知，再考虑邮件或 Webhook；通知需要去重、重试、投递状态、敏感信息最小化和用户退订。任何真正的自动交易都应作为独立的高风险项目重新评审。
