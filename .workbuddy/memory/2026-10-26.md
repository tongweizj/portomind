**结论二分**：日志频道接「运行详情」（cron 有没有干活，数据源 taskruns，只读）；组合域接「提醒详情」（要不要动手，数据源 RebalanceRecord，含执行/撤销写动作）。判据：频道契约（FS 自己写 NG1 只读）、接口契约污染（`/api/cron/status` 按 NG3 不读 RebalanceRecord）、与 Dashboard 待处理提醒语义重复（重犯 FAM-03 / AL-07 已判「合并」的坑）、受众/权限、命名撞车。

**C-07 方案**：不新增独立详情页，改「卡内行内展开 + 双向互链」（日志→组合带 `?record=`，组合历史→日志带 taskrun 筛选）；n=3 撑不起独立 route。

**核查出的 6 处数据契约事实（会改 C-02/C-05 验收）**
1. `shared/models/taskRun.js` **无 `result` 字段**，mongoose strict 默认 → 写 `taskruns.result` 被**静默丢弃**。R5/OQ3/C-05 的「写入 result」前提不成立，须先加 schema 字段。
2. `shared/services/taskRunner.js:7-14` `normalizeCounts()` 是**白名单**（只留 totalCount/successCount/failureCount/failures）→ 任务 `return {ok,gap,alertsFired}` 同样被丢。只改任务不改此函数 = 无效。
3. `TaskRun.status` 枚举为 `RUNNING|SUCCEEDED|PARTIAL|FAILED`，**无 SKIPPED**（FS §1 的「4 态含 SKIPPED」错）；SKIPPED 只作返回值+日志、不落库 → 看板灰态无载体；`RUNNING` 会因进程崩溃留僵尸，看板须处理。
4. **再平衡分发无父级 taskrun**：`cronScheduler` 直接 `await execute()`，只有逐组合 `rebalance-suggestions:<pid>`；未到期/归档/整批崩溃 = **零记录** → 「到期 N」分母不可得（须从 Portfolio 算或补父任务行）。
5. 逐组合 taskrun 无论 `needsRebalance` 真/假都返回 `{totalCount:1,successCount:1}` → 「生成了几条建议」不可区分，须 C-05 补 `suggestionsCount`。
6. 唯一无阻塞：组合 FAILED 可显示，`failures[]` 有 item/category/message，外层 catch 也写 failures。

→ C-07 的真实依赖是 **C-05 而非 C-02**；否则空表会被渲染成健康，等同「全绿误导」换位重演。
