## 1. 产品定位与价值主线

> **本节是产品的唯一权威定义**。7 份产品线子文件的 §1 只写本线专属的定位与价值主张，产品是什么、为什么存在、边界在哪，一律引用本节，不再各自复述。

### 1.1 这个产品是什么

PortoMind 是**自托管、单用户（一个家庭）**的投资组合账本 + 决策辅助系统——把「我买了什么 / 现在值多少 / 离目标差多少 / 该不该调」这四件事，从「Excel + 券商 App + 行情网站」的手工拼凑，收成一个**每天自动更新、口径唯一、可逐层下钻**的本地系统。

它替掉的是三件手工活：

| # | 原来你得自己做 | 现在由谁做 |
|---|---|---|
| 1 | 每天抄收盘价、抄汇率 | 定时任务自动入库（价格 / 完整性 / 提醒 / 汇率 / 再平衡巡检） |
| 2 | 手算持仓成本、盈亏、各标的占比 | 移动平均成本引擎：交易一改，整账重放，历史持仓可回溯 |
| 3 | 手判「要不要再平衡、要卖多少」 | 绝对偏离 + 相对偏离 + 时间间隔三判据 → 先卖后买的建议清单 |

| 它是 | 它不是 |
|---|---|
| 家庭 ETF / 基金 / 个股的组合账本 | 券商或下单通道 |
| 目标配置与偏离的监控器 | 消费 / 记账 App |
| 再平衡建议生成器（先卖后买清单） | 自动交易机器人（AUTO 只出建议） |
| 站内提醒中心（到期 / 偏离 / 估值） | 多租户 SaaS（本产品是**单租户多账号**：所有账号共享同一份家庭数据，已有登录与 `admin`/`member` 角色） |
| 家庭人民币口径的汇总层 | 行情终端（只看持仓与关注标的） |

### 1.2 核心业务闭环与使用形态

```text
资产主数据 → 交易流水 → 持仓/盈亏 → 目标配置 → 再平衡建议 → 提醒中心 → 家庭 RMB 汇总
                              ↑                              ↑
                       行情价格同步（每日）            汇率采集（每日）
```

**日常节奏**：凌晨跑完全部定时任务，白天系统是「静」的。**它不需要你每天录入**——只在你想看一眼、或收到一条站内提醒时才打开；只有「有再平衡待办」时才需要动手。

**典型使用形态**：三个互相独立的组合——CN-稳钱（人民币·稳健）、CN-长钱（人民币·长钱）、CA-长钱（加币 + 美金·长钱）——之上再有一层「家庭整体资产配置」。这就是「跨币种只在家庭层折算」的由来，不是实现妥协。

### 1.3 三条不可让渡的边界

| 边界 | 产品含义 | 失效后果 |
|---|---|---|
| **绝不下单** | AUTO 再平衡只产出建议 + 提醒，执行永远由人点 | 定时任务若写了交易，系统就从「建议者」变成「代客操作」，信任前提崩塌 |
| **缺价不猜** | 缺价时估值字段为 `null`，绝不按 0 计 | `null` 会静默扩散成整条链路的「—」；采集失败必须**可被发现** |
| **只有家庭层折算** | 组合内不跨币种加总；到家庭层才乘汇率 | 汇率与价格是同一等级的可信前提，任一断链都让家庭数字失真 |

> 这三条是全部产品线判定的前提：任何功能若违反其一，无论体验多好都不予采纳。它们也解释了为什么「平台基座线（PL-0）」必须存在——上述任一边界失效，最终都以**用户看到的错误数字**出现，而不是报错。

### 1.4 三条价值主线

从产品视角，用户真正付费（时间/信任）购买的不是「功能列表」，而是三句话：

| 价值主线 | 用户原话（目标状态） | 对应能力 |
|---|---|---|
| **记得准** | 「我录进去的每一笔都是真的，系统算出来的持仓和券商一致」 | 账本、成本引擎、行情 |
| **看得清** | 「我一眼知道每个账户结构对不对、全家一共多少钱」 | 组合、目标配置、家庭总览 |
| **动得对** | 「偏离了、该关注了，系统告诉我具体怎么动」 | 再平衡、提醒、信号 |

全部已有功能应当能被这三条主线解释；解释不了的功能，就是评估中需要「合并 / 删除 / 降级」的候选。

## 2. 产品线划分

### 2.1 划分原则

| 原则 | 说明 |
|---|---|
| 按**价值主张**而非技术模块划分 | 产品线对应一句用户价值，而不是一个代码目录 |
| 一个产品线内模块**共享同一批用户目标** | 便于独立评估成熟度与投入产出 |
| 区分**价值线**与**支撑线** | 面向用户的 6 条线 + 1 条平台基座；基座不直接交付价值，但决定上层可信度 |
| 产品线之间**依赖单向清晰** | 上游断链会直接让下游「显示 —」或不可用 |

### 2.2 产品线总表

| 编号 | 产品线 | 价值主张（一句话） | 主要用户 | 成熟度 | 明细 |
|---|---|---|---|---|---|
| **PL-1** | 投资账本线（Ledger） | 忠实记录每一笔真实交易，自动推导持仓与成本——系统的**唯一事实来源** | 家庭投资主管 | 较完整 | [→ PL-1](./lines/PL-1-ledger.md) |
| **PL-2** | 行情数据线（Market Data） | 每日自动获取多市场行情与估值分位，是估值 / 盈亏 / 提醒的**输入底座** | 系统（无人值守） | 较完整 | [→ PL-2](./lines/PL-2-market-data.md) |
| **PL-3** | 组合与配置线（Portfolio） | 把每个真实账户建成独立记账单元，设定目标配置，**看清结构与漂移** | 家庭投资主管 | 完整 | [→ PL-3](./lines/PL-3-portfolio.md) |
| **PL-4** | 再平衡决策线（Rebalancing） | 偏离阈值 → 给出先卖后买的可执行建议 → 确认后生成内部交易 → **可撤销/重做** | 家庭投资主管 | 完整 | [→ PL-4](./lines/PL-4-rebalancing.md) |
| **PL-5** | 提醒与通知线（Alerting） | 把「该看 / 该买 / 该卖」变成**可行动的站内信号** | 家庭投资主管、家庭共同所有者 | 完整 | [→ PL-5](./lines/PL-5-alerting.md) |
| **PL-6** | 家庭总览线（Household） | 跨账户、跨币种，以 RMB 一屏看清**家庭总资产** | 家庭共同所有者、家庭投资主管 | 较完整（仅「看」不「动」） | [→ PL-6](./lines/PL-6-household.md) |
| **PL-0** | 平台基座线（Platform Foundation） | 调度、数据质量、可观测性、设计一致性——决定上面六条线的**可信度** | 自持运维者 | 可用但有技术债 | [→ PL-0](./lines/PL-0-platform-foundation.md) |

> **为什么要拆出 PL-1 与 PL-3/PL-4**：
>
> 账本是「事实来源」，组合与再平衡是「决策层」。二者共用「持仓」概念但目标不同——账本关心「算得对」，决策层关心「调得准」。混在一起会导致「修正账本」和「调整配置」的需求互相污染。

### 2.3 产品线依赖关系

```text
PL-2 行情数据 ──────────────┐（价格/估值输入）
                            ▼
PL-1 投资账本 ────────> PL-3 组合与配置 ──┬─> PL-4 再平衡决策
   （交易→持仓）          （目标/漂移）    │
                            │             └─> PL-5 提醒与通知
                            │                    ▲
                            └─> PL-6 家庭总览 ───┘（待处理提醒入口）
                                  ▲
PL-2 行情数据 + 汇率 ─────────────┘

PL-0 平台基座 ──横切驱动──> PL-1 / PL-2 / PL-3 / PL-4 / PL-5 / PL-6
```

**读法**：

上游是下游的前置条件。

典型断链后果——PL-2 缺价 → PL-1 市值/盈亏为 `null` → PL-3 漂移为 `null` → PL-4 无法生成建议（`MISSING_MARKET_PRICE`）→ PL-6 该组合不计入总额。

这解释了为什么「数据质量」被提升为**产品级信任项**而非纯技术项。

## 4. 评估框架与总览统计

> 逐条判定表已下沉到各产品线子文件（[PL-0](./lines/PL-0-platform-foundation.md) ~ [PL-6](./lines/PL-6-household.md)）；本节只保留**共用判定标准**与**跨线汇总**。

### 4.1 判定标准

| 判定 | 定义 | 触发信号 |
|---|---|---|
| **保留（Keep）** | 已达到产品目标，无需改动 | 无缺口、无歧义、无维护风险 |
| **强化（Strengthen）** | 方向正确但深度 / 完成度不足，需**增加能力** | 用户目标已达成一半；缺关键子能力 |
| **修改（Modify）** | 方向对但**规则 / 边界 / 体验**存在问题，需**改定义** | 规则不合理、口径不一致、存在隐患 |
| **合并（Merge）** | 存在重复实现或重复描述，应**收敛为一处** | 同物多名、多份实现、重复入口 |
| **删除（Delete）** | 死代码 / 空实现 / 已被取代，应**清除** | 未接入路由、0 字节文件、被替代 |

**评估原则**：① 优先消除**维护成本**（个人 / 小团队维护下，重复实现的成本远高于功能缺失）；② 优先修复**信任风险**（账本口径、资损式错误、静默失败）；③ 不为了「功能更多」而保留低价值能力。

### 4.2 总览统计

| 判定 | 数量（约） | 占比 | 说明 |
|---|---|---|---|
| 保留 | 34 | 41% | 核心账本 / 成本 / 再平衡 / 提醒主链已扎实 |
| 强化 | 27 | 33% | 主要集中在录入体验、数据质量可视化、决策闭环最后一公里 |
| 修改 | 12 | 15% | 口径不一致（币种枚举）、~~安全隐患（CORS / 无认证）~~ ✅ 已闭环（TASK-058 U1，2026-10-27）、体验冗余（Tab） |
| 合并 | 6 | 7% | ✅ 双份调度已合并（TASK-005）；✅ 枚举降为两份；余：重复入口、双轨样式 |
| 删除 | 4 | 5% | 未接入组件 + 空文件 + 冗余维护接口 |
| **合计** | **83** | 100% | 覆盖原 `functions.md` 全部功能域 |

> **一句话结论**：**功能已经「不缺」**——六条价值线基本齐全、闭环成立。产品的下一阶段不是「加功能」，而是**补齐最后一公里 + 消除内部重复 + 把数据质量产品化**。

- **方法**：以原 `functions.md` 的 12 个功能域为全集，逐条对齐 PRD 功能编码进行产品判定；判定不改变任何代码，只产出「保留 / 强化 / 修改 / 删除 / 合并」建议。
- **假设**：① 产品长期面向「家庭内 1–2 人使用、自托管、无公网」；② 维护者为个人 / 小团队，重复实现的机会成本高；③ 「不自动交易」的安全边界不改变。
